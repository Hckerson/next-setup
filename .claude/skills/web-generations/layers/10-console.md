# Layer 10: Console

`components/sections/`. A composed working surface: header, status band, filters, table or list, detail rail. Where an operator spends the day.

**Upstream:** Token, Primitive, Pattern, Row, List and modal. A recurring tell here is usually inherited from these layers: trace it there and fix it once, not once per file here.

## Tells

## Floor versus baseline

A competent fourth-generation console is functional and good looking: KPI cards, a chart pair and an activity table, each in its own card, with a sheet for every row. It lacks a layout derived from the operator's question, filter and selection state that persists, detail beside the list, a keyboard path through the main actions, and complete state per region. The register decides how dense it is, how loud its chrome is and whether shortcuts are shown.

## Baseline

Every register meets these. Counts are of the 18 exemplars (`references/classification-ledger.md`, section 10).

- **CON-B1. Layout follows the question.** The layout is derived from the operator's question: the most-used region gets the most area, and equal cards appear only for equal items. `(S 2/18)` Stripe and Vercel overviews (as SEC-B8). Thin evidence.
- **CON-B2. Visible, persistent filters.** Filter state is persistent and visible, with counts where they help. The facets are the product's own. `(S 3/18)` Stripe analytics, Vercel deployments, Mercury.
- **CON-B3. State in the URL.** Filter, sort and selection state lives in the URL, so a reload or a shared link restores the view. `(J)` Thin: not measured; none breaks it.
- **CON-B4. Detail beside the list.** Detail never navigates away: it opens in the pane, or in a panel docked beside or below that does not cover the list. `(S 2/18)` Linear in the pane; Stripe's docked assistant and developers drawer. Thin evidence.
- **CON-B5. A keyboard path.** The console's main actions have a keyboard path. `(S 3/18)` Raycast's action panel, Linear's menu shortcuts, Mercury's Command item and shell. Showing shortcut hints in the UI is a register position (developer-tool, industrial).
- **CON-B6. Complete state per region.** Each region has its own loading skeleton in the final layout, empty, error with retry, and permission states; one region failing does not blank the console. `(J)` Thin: not measured; none breaks it.
- **CON-B7. Density is a token.** Density is a token decided per product and recorded in the brief; a console is where it matters most. `(S)` As ROW-B11: every register records a density position; the value is the register's.
- **CON-B8. Containers only where grouping needs them.** Regions nest containers only where grouping needs it, and the region treatment is one recorded decision (SEC-B12). `(J, thin)`

## Techniques

Register-neutral methods, recommended, not required.

- **Views as tabs.** Saved views as tabs over one dataset (Linear's view pills, The Pudding's filter tabs over its feed) fit any register; the pill styling is developer-tool.
- **URL state without jumps.** Write filter and sort to the URL with `router.replace` and `{ scroll: false }`, so the view keeps its scroll position.
- **Skeleton parity.** A test that renders a region's skeleton and its loaded state at one viewport keeps their geometry in step.
- **Stable positions.** Keeping panel positions and command names fixed across releases lets an operator learn a dense surface (Bloomberg Terminal, UNVERIFIED).
- **Charts.** Series colours from tokens, direct labels where the series are few, and one highlighted series that answers the question. Not measured in any exemplar (ledger 10.9 is UNKNOWN); capture before treating it as a criterion.

## Token roles this layer needs

Header, status band and rail dimensions; row height by density; chip states; docked-panel width; skeleton geometry; chart series colours; region treatment.
